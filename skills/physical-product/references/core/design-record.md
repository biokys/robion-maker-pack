# Design record — the project's memory of what was decided

One file in the project root answers "where is this design, what did the user
decide, what did I decide for them, and what is out of date" — for this session,
for the next one, and for Robion's design panel:

```
<project>/design.json
```

The transcript is not that memory: it is lost on a fresh session, it fills up
with render output, and nobody can edit an answer in it. The record is a plain
JSON file, committed with the sources, regenerated by nothing — you write it.

## Rules

- **Create it at the end of the brief analysis** (SKILL.md §1 step 1), before
  the question round: idea, spec, routed verticals, the stage list with every
  stage `pending`. The project directory exists by then (the task's working
  directory); scaffolding (§4) comes later and never touches this file.
- **Update it at every gate** — an answered question round, the concept
  freeze, each stage of §5 — and whenever a change request arrives (§7). A
  gate is not passed until the record says so.
- **Status discipline — the map is only as true as these three moves.** Before
  every stop-and-wait (the question round, the concept approval, every §5
  gate) set that stage `needs_you` and write the file; while you produce a
  stage set it `working` (add `startedAt` and a rough `estimate` in the user's
  language, from the project's "Cost of a change"); when the user approves,
  `done`. At creation: `idea` done, `brief` needs_you, the rest `pending`.
  Exactly one stage is `working` or `needs_you` at a time.
- **Every answer records who decided.** `decidedBy: user` when the user
  answered, `default` when they accepted the recommended default, `claude`
  when you chose (a fact the user cannot know, or an explicit "decide for
  me") — then `reason` is mandatory and the same sentence goes into the build
  sheet's assumptions section.
- **Stage ids are fixed** (below); the app's map relies on them. Labels are
  yours, in the user's language. A stage the stack has no equivalent for
  (analysis on a sewn bag) is `skipped` with a note, never removed.
- **A change after a gate is logged, not silently absorbed.** Append a
  `changes` entry naming what changed and which done stages it invalidates,
  set those stages to `stale`, tell the user, then regenerate in order.
  Stale means "was done, inputs changed since"; it becomes `done` again only
  after the stage is regenerated.
- **Structure in English, content in the user's language.** Keys, ids, enums
  and timestamps are the standard; `label`, `summary`, `answer`, `reason`,
  `note`, `title` are written the way the user speaks.
- **Paths are project-relative** and point at real files (`out/viz_hero.png`,
  `model.py`); the app shows them as thumbnails and links.
- **Never store secrets, absolute paths, or the transcript.** The record is
  small — one screen of JSON, not a log.
- **Omit what you do not know.** Leave a field out rather than writing `null`
  (the app tolerates `null`, but an absent key reads as "not yet"). Never
  paste the record into the chat — the user sees it in Robion's design panel.

Field notes:

- `stages[].status` ∈ `pending | working | needs_you | done | stale | skipped`.
  `working` = you are producing it now; `needs_you` = the gate waits for the
  user; `done` = the gate passed. Exactly one stage is `working` or `needs_you`
  at a time — that is the "current" stage.
- `stages[].artifacts` — the files the stage produced (project-relative).
- `questions[].id`, `concept.variants[].id`, `recommended`, `chosen` — lowercase
  snake_case (`[a-z][a-z0-9_]*`), at most 40 characters, stable across the
  project. A question id is also the control `key` on the Robion `brief`
  panel, and a variant id the option `value` of its card, so a changed control
  and a record entry name the same thing. `a`, `b`, `frame_stretchers` — never
  `A`, `v-1`, `Variant B`.
- `stages[].estimate` — free text in the user's language ("about 6 minutes"),
  set together with `working` and `startedAt`; the app shows it while the
  stage runs. `changes[].cost` — the same for a change ("model and previews,
  ~10 minutes").
- `concept.variants[].facts` — a flat object of numbers the user compares
  (mass, hours, stiffness ratio, cost only when the profile gives prices).
- `changes[].what` — a dotted path into the record (`questions.width`,
  `concept.chosen`, `spec.summary`).

## The ten stages

| id | SKILL.md | Gate |
|---|---|---|
| `idea` | §1, the user's words | exists as soon as the record does |
| `brief` | §1 step 1–2 (brief analysis + question round) | answers recorded |
| `concept` | §1 step 3 (concept gate) | `concept.chosen` + `frozenAt` |
| `model` | §5 stage 1 | user approves the live geometry |
| `preview` | §5 stage 2 | user approves proportions |
| `drawings` | §5 stage 3 (drawings or pattern sheets) | every PNG read and checked |
| `bom` | §5 stage 4 (BOM + cut plan / marker) | masses cross-checked |
| `plan` | §5 stage 5 (assembly / sewing / welding plan) | executable order |
| `analysis` | §5 stage 6 (analytic + FEA; `skipped` when not load-bearing) | sanity checks pass |
| `buildsheet` | §5 stage 7 | user approves |

## The brief panel in Robion

Robion (0.13 and newer) draws the map of stages, the answers and the change
log straight from the record in its design panel — the panel carries only what
the user must *do*. When `set_controls` exists, build a task-scoped panel named
`brief` right after the record exists, before the first question, and then
only ever `mode: 'merge'` into it (the default `replace` wipes the answers and
the map of what changed):

- **Question round** — a `select` / `toggle` / `text` per question, `key` =
  the question id. Every select carries `default` = the recommended value and
  `decide_for_me` as its *first* option (labelled in the user's language); a
  select without `default` would silently answer `decide_for_me`. One `send`
  button returns the answers as the next prompt (`text: 'answers: width=${width},
  finish=${finish}, …'`); the value `decide_for_me` in that text is the only
  signal for `decidedBy: claude`. Questions a select cannot hold go in the
  chat with the same ids.
- **Concept gate** — a `choices` control keyed `variant`, `width: 'full'`:
  one option per variant with `value` = the variant id, `label`, `description`,
  `image` (the quick preview) and `tags` (mass, hours, stiffness); a `send`
  button `confirm_concept` with `enabledWhen: {key: 'variant', op: 'truthy'}`
  so nothing goes out before a card is picked. Later stages add a `gallery`
  (views of the chosen variant) or a `table` (BOM, cut list), both
  `width: 'full'`.
- **Next steps as buttons.** Whenever you stop for a decision — a gate, the
  question "regenerate now?" after a change — put the choices on the panel as
  `send` buttons (`continue`, `wait`, `back`) with plain labels in the user's
  language. The user reads the panel, not the terminal.
- **A change from the app.** Robion's design panel lets the user edit a
  recorded answer; it arrives as a prompt naming the question's label and id,
  the old and the new value. Treat it as the change protocol below, and also
  bring the panel in line: re-define that control with `mode: 'merge'` and the
  new value as `default` (if the old value is still a valid option, call
  `remove_controls` for the key first so the value resets). The prompt carries
  display text; the record keeps the question's original type (number, boolean,
  list).
- Never `remove_controls` the whole panel. Bare terminal (no `set_controls`),
  or a Robion older than 0.13: the record alone; ask in the chat and say the
  stage status in words.

## Change protocol (§7 in record terms)

1. Identify what changed: a question, the chosen concept, a spec sentence, a
   parameter after the freeze. Update that field; set `decidedBy` /
   `answeredAt` again.
2. Append a `changes` entry; list in `invalidates` every `done` stage whose
   inputs it touches — by default every done stage after the changed one
   (linear); keep a later stage `done` only when you can say why it is
   unaffected (a finish change does not invalidate the cut plan). Put the
   rough cost in `cost` ("model and previews, ~10 minutes").
3. Set those stages `stale`, tell the user what will regenerate and how long
   (the project CLAUDE.md "Cost of a change" section), and continue from the
   first stale stage. Expensive stages wait for the user's go — offered as
   `continue` / `wait` buttons on the `brief` panel, not only as a question in
   the chat.
